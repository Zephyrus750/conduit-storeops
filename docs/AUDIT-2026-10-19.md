## Summary

- One critical problem: a phone can silently stop sending its changes after a moment offline, and keep showing them as if they were sent (D1). With D2, queued work is then deleted when the area code lapses or a new feature deploys. Together they can lose a night’s scans with nobody seeing it. Both are small fixes.
- Three security holes, each a small fix: an encoded slash lets a store-PIN phone read owner-only data (S1); a device signed out by the owner can sign itself back in (S2); ids and names can carry HTML that redirects other devices to a fake page (S3).
- Growth: a store’s live data outgrows the worker’s 2 MB snapshot within about two months of normal use, after which the store slows and eventually stops starting (D3). There are no backups (D5).
- Speed: product names fail on any screen that needs more than 50, which is the likely cause of product names opening a search instead of the product page (P1). Attaching a manifest takes about 3.5 seconds and blocks the store meanwhile (P2).
- Releases: the site goes live about a minute before the worker on every merge (T1), and every site, previews included, writes to the pilot store’s worker (T2).
- The foundations are sound: sign-in, passwords, permission checks on every change, the site’s security policy, escaping of free text, and the reducers all held up under targeted testing (see “Checked and sound”).

## 1. Data safety

What could lose, duplicate or corrupt a store’s work.

### D1 · A phone stops sending its changes after one offline moment

Critical · Reproduced · effort S · Fix first

If the outbox tries to send while the phone is offline (or while the retry breaker is open after a few timeouts), it never sends again until the app is reloaded. The phone keeps showing its own scans, so nobody notices, but the desk and other devices never receive them. Reproduced against the real worker: 4 scans queued on the phone, 0 on the server, after the network came back.

**Evidence**

- `client/store.js:135-155`: `flush()` returns before its first `await` when offline, so its `finally { flushing = null }` runs before the outer line assigns the promise to `flushing`. `flushing` then stays set for good and every later `flush()` returns it without sending.
- The contract test passes only because it builds a second store instance (`test/contract/client.test.js:62,71`).

**Fix.** Assign the promise before running and only clear your own (`const run = (async () => { await null; … finally { if (flushing === run) flushing = null } })(); flushing = run`). Also flush on the browser’s `online` event. Add a test that takes one store instance offline, then online, then flushes.

### D2 · Queued work is deleted when the area code lapses, or when the worker is behind

High · Reproduced · effort M · Fix first

Changes waiting in a phone’s outbox are refused and then deleted if the Stockroom or Dock code has lapsed by the time they send: the idle re-lock, the 12-hour role expiry, or switching store all do this. The same deletion happens to a new kind of change sent in the minute after a deploy, before the worker has updated (the “unknown type” error you hit with No trucks). With D1, a phone stuck overnight loses the night’s scans when its code expires.

**Evidence**

- `client/store.js:157-168` deletes every refused event before reporting it.
- `client/session.js:55-60,122-126` and `worker/registry.js:224-226` drop the code on lock, park and role expiry.
- Reproduced: 4 queued cage events refused `unauthorised` and removed, none on the server.

**Fix.** Split refusals in two. Permanent (invalid data, a real conflict): drop and tell the person. Waiting (`unauthorised`, `not_entitled`, `tool_off`, `clock_skew`, unknown type, server error): keep them queued, marked with the reason, show “3 changes wait for the Stockroom code” or “waiting for the server update”, and retry after unlock or update. Flush before locking or switching store, and warn if area work is still queued.

### D3 · A store’s live data outgrows the 2 MB snapshot, and then the store slows and can fail to start

High · Measured · effort L · Next

The worker saves the store’s live state as one 1.9 MB row so it can restart quickly. Retention does not keep the state under that. Built with the real reducers over 60 days, a light store with no back dock (30 bays a day) comes to 3.4 MB after retention, and a store with five trucks a week to 11.5 MB. Once over the limit, snapshots stop for good: every change gets slower (7 ms to 27 ms each, with an error logged each time), and every restart replays all events since the last snapshot, a list that only grows. Measured 1.5 to 2 seconds at about 8,000 events; at 80,000 the estimate is around 150 seconds of work, past Cloudflare’s 30-second start limit, so the store would stop starting. Check Busselton’s size on the owner Service page: it flags a store over 1.2 MB.

**Evidence**

- `worker/store.js:112-125` skips the snapshot when `text.length > SNAPSHOT_MAX` and never resets the counter; `load()` (`:99-109`) reads the whole replay with `toArray()`.
- `shared/retain.js` never prunes closed cages, APN pairs, pick lists or refresh focus; closed trucks keep pallets and manifest lines for 60 days; the consolidation ledger keeps 60 days.
- Largest slices measured: dock 6.1 MB (trucks 4.5, manifest lines 2.1, ledger 1.6), backfill 1.0–2.3, refresh 0.6–1.2, cages 0.3–0.6.

**Fix.** Two parts. Make snapshots never skip: store them in chunks or one row per slice, back off and report once a day if one fails, and read the replay with a cursor. Then shrink what lives in state: a closed truck keeps only its history row (pallets and lines come from the stored manifest or the archive), the ledger moves to its own table, bays archive after 14 days, refresh weeks older than the current two keep counts only, and closed cages, APN pairs and pick lists get retention. Target: a typical store at 0.5–1 MB, which also speeds up P3 and P4.

### D4 · A device can apply its own change twice, or out of order

High · Reproduced · effort M · Next

When a change is confirmed over the normal web connection (the fallback when the live socket is down or reconnecting), the device folds it straight into its saved copy, ahead of earlier changes it has not received yet, and it forgets which changes it has applied when the app reloads. Reproduced three ways: a cage quantity of 2 showing as 4 after a reload; the same after a snapshot and a repeated confirmation; and two people editing the same issue title, where the worker kept one title and the device kept the other, for good.

**Evidence**

- `client/store.js:83-91`: own events skip the `seq <= base.seq` check and are applied immediately; `:167` folds every HTTP confirmation.
- The set of applied ids (`:33`) is never saved, so a reload re-applies.

**Fix.** Keep confirmed own changes in a separate list ordered by sequence number and replay it on top of the saved copy until the stream catches up. Treat everything at or below the saved sequence as already applied. If the device ever refuses an event the server accepted, ask for a fresh snapshot instead of carrying on.

### D5 · No backups, and a restore would leave devices blind

High · Reproduced · effort M · Next

Nothing backs up a store’s event log, manifests, SOH snapshots, inventory reports or maps, or the registry of stores and credentials. Cloudflare keeps 30 days of point-in-time recovery for this kind of storage, but nothing uses it and there is no written procedure. Worse, after a restore the store’s sequence number goes backwards, and devices that had seen higher numbers skip every new event (reproduced: a device at 2,400 never saw the new change made at 1).

**Evidence**

- No export of the event log anywhere; the CSV exports cover four record kinds only, and `/tail` the newest 1,000 events.
- Hello with `since` above the server’s sequence returns an empty delta (`worker/store.js:660-663`), and the client skips `seq <= base.seq` (`client/store.js:87`).

**Fix.** From the nightly run, append the day’s events (plus manifest, SOH, report and map rows) to R2 as one file per store per day; add an owner “Download event log”. Write a short runbook for point-in-time recovery. Give each store’s log an id that changes on restore, sent with snapshots and hello, so a device with a different id or a higher sequence takes a full snapshot.

### D6 · “Apply to map” renames every shelf that shares the old name

Medium · Reproduced · effort S · Fix first

A Field Mode rename of a duplicated shelf name (the very case that prompts a suggestion) renames all the shelves with that name, so the real one disappears. The confirm counts suggestions, not shelves, so it reads “Apply 1 change” while changing two.

**Evidence**

- `shared/mapedits.js:26-30` renames every match on the floor; rename suggestions carry no position.
- `js/views/admin.js:560-563`: the confirm counts suggestions.

**Fix.** Refuse unless exactly one shelf matches, carry the tapped position on rename suggestions and match by it, and show how many shelves will change.

### D7 · A manager’s own device refuses a late manifest attach that the worker accepts

Medium · Reproduced · effort S · Fix first

Attaching or linking a manifest to a finished truck needs the manager code. The worker checks the manager role correctly, but the manager’s device checks its first role, which is always Floor, and refuses before sending.

**Evidence**

- `client/store.js:124,167` use `roles[0]`; the worker uses `primaryRole`; `shared/reducers/backdock.js:676` requires `actor.role === "manager"`.

**Fix.** Move `primaryRole` into `shared/` and use it for the device’s own check and its own fold.

### D8 · Receiving history past 500 trucks is dropped instead of archived

Medium · Measured · effort S · Fix first

The reducer trims receiving history to 500 rows on the 501st truck, so nightly retention, which archives anything beyond 500, never sees a row to archive. Old trucks vanish from History and its CSV.

**Evidence**

- `shared/reducers/backdock.js:47,286,765` cap at `HISTORY_CAP = 500`; `shared/retain.js:32` archives only beyond `KEEP_DOCK_HISTORY = 500`.

**Fix.** Cap the reducer above the retention limit (for example 1,000 against 500), or trim only in retention. Add a test for the 501st truck.

### D9 · Label check cycles: the wrong cycles are kept

Medium · Reproduced · effort S · Next

Retention sorts cycle ids as text. After a store switches its label checks from weekly to monthly, the old weekly cycles are kept and the current month’s checks are deleted every night. Fortnight ids also collide at the turn of the year (30 Dec 2025 and 2 Jan 2025 both become `2025-F01`).

**Evidence**

- `shared/retain.js:19,74` (`keepNewest` sorts text); `js/ui.js:111-116` builds the fortnight id from the calendar year with the ISO week.

**Fix.** Order cycles by their start date, and build fortnight ids from the ISO year.

### D10 · An older inventory report can replace a newer one

Medium · Reproduced · effort S · Next

A desk that pasted a report while offline sends it when it reconnects, without checking whether another desk has pasted a newer one since. The worker keeps whichever arrives last, so a one-bay paste from 08:00 replaced a 300-bay paste from 09:00 in the reproduction.

**Evidence**

- `js/views/stockroom/bfreview.js:143,155-165` push the unsent copy as is; `worker/store.js:465-485` uses `INSERT OR REPLACE` with no check.

**Fix.** Send the revision the paste was based on and have the worker answer 409 if it has moved on; the desk then fetches and merges by bay. At minimum, refuse a report older than the stored one.

### D11 · A device on the polling fallback can stall for good

Medium · Reproduced · effort S · Next

When the live socket is blocked (some store networks do this), devices poll for changes in pages of 5,000. The page is cut before filtering out areas the device may not read, and the device ignores the “more” flag, so after 5,000 events it cannot read (for example a Floor phone during a busy dock day) it never sees another change.

**Evidence**

- `worker/store.js:217-222` applies `LIMIT 5000` before the area filter; `client/store.js:236-237` ignores `more` and the returned position.

**Fix.** Return the position of the last row scanned; the device stores it and keeps polling while `more` is true.

### D12 · Truck clear time and team rate are wrong after someone edits pallet times

Medium · Reproduced · effort S · Next

Edited times are saved in UTC (`…Z`) while normal pallet times are saved in store time (`+08:00`). History picks the last finish time by sorting text, so the wrong one wins: a clear time of 210 minutes was recorded as 120.

**Evidence**

- `js/views/backdock/receiving.js:328` sends `toISOString()`; `shared/reducers/backdock.js:869` and `js/views/backdock/audit.js:20` take the last time by text sort.

**Fix.** Pick the latest time by its real instant (`Date.parse`), and have edits write store-time values.

### D13 · After a rule change, a restart can quietly rewrite history on the worker

Medium · Reproduced · effort M · Next

When the store restarts, it replays recent events with today’s rules and silently drops any that the rules now refuse. Devices still show the old outcome, so the two disagree. In the reproduction, a bay submitted before the “not reviewed” rule existed went back to pending on the worker only.

**Evidence**

- `worker/store.js:105` ignores the rejections `replay` returns.

**Fix.** Report replay rejections, and treat logged events as facts on replay (apply without the newer guards, or tie guards to the event’s version).

### D14 · After a reload, queued changes can send in the wrong order

Medium · Reproduced · effort S · Next

The outbox is re-sorted by event id after a reload, and the id contains the device’s clock. If the clock was corrected while changes were queued, a scan can be sent before the cage it belongs to; it is refused and deleted.

**Evidence**

- `client/store.js:112` sorts pending events by ULID.

**Fix.** Save a per-device counter with each queued change and sort by that.

### D15 · Smaller data issues

Low · Mixed · effort S · Later

Grouped low-severity items, each reproduced or traced in code.

- A device whose clock is more than 10 minutes fast loses its first changes as `clock_skew` before it learns the offset (seed the offset at sign-in; retry, do not delete).
- `plan.set` with a malformed slot manifest throws after it has already cleared the day’s No-trucks mark (`shared/reducers/backdock.js:110-112,602`); validate the consols first.
- Removing a manifest that a planner slot stages by reference leaves the slot pointing at nothing (`worker/store.js:448-455`); refuse with 409 while referenced.
- A text value for expected minutes becomes `NaN` in memory and `null` after a snapshot (`backdock.js:369`).
- SOH and report dates are not checked against the store day (`2027-03-01` and `2026-02-30` accepted).
- Some screens use the device’s date instead of the store’s: planner day keys (`planner.js:12-13,74`), the dashboard’s “tomorrow”, `mondayOf` in Manifests. Only matters on a device set to another time zone.
- Two quick taps on the pick list can lose the first (`client/store.js:126-128`).
- A double tap on Field Mode’s Send sends every capture twice (`js/views/fieldmode.js:83-96`).
- A retried change that already landed is reported “unauthorised” if the code lapsed in between, because the duplicate check runs after the role check (`worker/store.js:258-266`).
- Some changes are accepted with no effect (a second `halt.start` while one is open drops its reason; an empty `issue.update`), against the “nothing silent” rule.
- Times compared as text in a few reducers (`floor.js:280`, `retain.js:75`, `backdock.js:285`), and sort comparators that return no 0 for ties.
- Each desk keeps up to 1.9 MB of old inventory-report copies per day until cleared by hand in Settings.

**Fix.** Fix alongside the related larger items; each is small.

## 2. Security

Who could see or do what they should not.

### S1 · An encoded slash in a link reaches owner-only data

High · Reproduced · effort S · Fix first

A Floor phone (store PIN only) can read the raw event log of every area, including stockroom adjustments and truck events, plus the device list and the store’s KPIs, by putting `..%2F` into a link. These are meant for the owner. Reproduced: `GET /v1/store/1241/life/..%2Ftail` returned the full log to a Floor-only token that correctly gets 403 on the real route.

**Evidence**

- `worker/router.js:180` decodes `%2F` into `/`; `worker/index.js:354` builds `https://store/life/../tail`, which the URL parser turns into `/tail`.
- `worker/store.js:159-162`: `/devices`, `/kpis` and `/tail` have no check of their own.
- Any route with a second parameter works: `life/:keycode`, `map/:version`, `history/:kind`, `manifest/:manNo`, `photo/:id`, `soh/:date`.

**Fix.** Check each route parameter before forwarding (store digits, ULID ids, dates, `[\w.-]` names) and refuse `/`, `\`, `%` and `..`. Also make `/tail`, `/devices` and `/kpis` check the owner inside the store object. Add a contract test that tries `..%2F` on every parameter route.

### S2 · “Sign out every device” does not keep a lost device out

High · Reproduced · effort S · Fix first

After the owner signs every device out (or rotates the PIN), a device that still holds its access token (valid up to 12 hours) can call the idle re-lock route, get a brand-new refresh token, and carry on reading and writing. Reproduced end to end, including a write accepted after the revoke.

**Evidence**

- `worker/index.js:70-78`: `/v1/auth/lock` checks only the token’s signature and expiry, then issues a refresh token.
- `worker/registry.js:207-229`: refresh rows do not record the epoch, and using one stamps the current epoch onto the new token. `/unlock` does check the epoch (`:147`).

**Fix.** Refuse `/lock` when the token’s epoch is older than the store’s. Store the epoch on refresh rows and refuse rows from an older epoch.

### S3 · Names and ids can carry HTML into other devices’ screens

High · Reproduced · effort S · Fix first

The event checker allows `<`, `>` and quotes in ids and names, and a few screens insert those ids without escaping. Anyone with the store PIN can log an issue or set refresh focus departments with markup in the id, and every device that opens Maintenance or Location refresh renders it. The site’s security policy stops scripts, but injected HTML still works: in testing, an injected refresh tag redirected the page. So a PIN holder could send every desk to a lookalike page that asks for the manager code. A label assignment without a `-` also stops Label integrity opening on every device.

**Evidence**

- `shared/validate.js:28-35,52-66` only limit length and block prototype names.
- Unescaped sinks: `js/views/maintenance.js:224` (`data-id="${i.id}"`), `js/views/refresh.js:191,218` (focus departments), `js/views/labelint.js:164-199` (micro keys), `js/views/stockroom/adjust.js:44` (day key in `title`).

**Fix.** One change closes the whole class: in `shared/validate.js`, only allow plain characters in entity values (`[\w .:/-]`). Also escape those four sinks, and guard `microName` against a key without `-`.

### S4 · Anyone can stop new sign-ins at a store

Medium · Code · effort M · Next

Sign-in failures count against the store as a whole, from anyone, and the list of store numbers is public. Thirty wrong guesses lock new sign-ins for 15 minutes; after that, one more wrong guess re-locks it for the rest of the hour. Devices already signed in carry on, but nobody can sign in a phone or a manager PC.

**Evidence**

- `worker/registry.js:124,170-176`: the store key is checked first for every device; `worker/index.js:97` lists store numbers.

**Fix.** Give each device a secret at its first successful sign-in and exempt known devices from the store-wide count, as owner devices already are. Add per-IP rate limiting on `/v1/auth/*` (Cloudflare rule or the Workers rate-limit binding), and tell the owner when a store locks.

### S5 · A stolen refresh token keeps working indefinitely

Medium · Code · effort M · Next

Refresh tokens rotate, but reusing an old one is not detected, so a copied token keeps a session alive on a 30-day rolling window. Owner sessions have no overall limit.

**Evidence**

- `worker/registry.js:214-229` deletes the used row and issues a new one with a fresh 30 days, with no token family.

**Fix.** Track a family per sign-in with an absolute expiry; if a used token is presented again, revoke the whole family. Cap owner sessions and add “Sign out all owner sessions”.

### S6 · Department colours in a published map are not checked

Medium · Reproduced · effort S · Next

A colour like `"><b>` published with a map is inserted into `style="background:…"` across the app, on every device. Only the owner can publish, but a mistaken or compromised owner key reaches every screen in the store.

**Evidence**

- `worker/store.js:613` keeps any 16 characters; `js/ui.js:85` (`dep()`) and many `background:${DEPT_COLOUR[…]}` sinks insert it.

**Fix.** Accept only `#rgb`/`#rrggbb` (or a named colour) in the worker and in `cleanStoreInfo`, as marker glyph colours already are.

### S7 · Product lookups can run up Cloudflare cost

Medium · Code · effort M · Next

The product catalogue routes need no sign-in and have no rate limit, and every request goes to one shared object. Any signed token (even one revoked in the last 12 hours) can make one request start up to 50 product-page renders in Browser Rendering, which is billed per browser hour, with no daily cap.

**Evidence**

- `worker/index.js:175-191`, `worker/catalogue.js:59-65`, `worker/details.js`.

**Fix.** Rate-limit per IP and per token; require a current store token for detail fetches; set a daily rendering budget per store.

### S8 · Oversized changes: counted in characters, stored in bytes, applied before saving

Medium · Reproduced · effort M · Next

The size cap on a change counts characters, but storage limits bytes, so text with accented or symbol characters can pass the check and still be too big to save (reproduced: about 838,000 characters became 2.3 MB). The worker has already applied it by then, so live data holds a change that was never logged, which is gone after a restart, and the sending phone retries forever. Separately, the Floor role may send 1 MB changes, extra fields are stored as sent, and restarts load the replay fully into memory.

**Evidence**

- `shared/validate.js:39` measures `JSON.stringify(payload).length`; `worker/store.js:278-286` applies, then inserts; `:271,285` store the payload as sent.
- `shared/catalogue.js:162-163` allow 1 MB for `inventory.offsite.set` and `inventory.load.add` with the Floor role.

**Fix.** Measure UTF-8 bytes; insert in the same transaction as applying, or reload on failure and answer `payload_too_large`; keep only the declared fields; lower the Floor limits; read the replay with a cursor.

### S9 · Two vendored libraries have published vulnerabilities

Medium · Code · effort S · Next

SheetJS 0.18.5, which reads manifest and inventory uploads on the desk, predates fixes for a prototype-pollution bug and a slow-regex bug. pdf.js 3.11.174 in the map editor has a code-execution bug; the site’s security policy blocks the eval it needs, which reduces the risk.

**Evidence**

- `vendor/xlsx` (`XLSX.version` 0.18.5: CVE-2023-30533, CVE-2024-22363).
- `editor/lib` pdf.js 3.11.174 (CVE-2024-4367); `getDocument` at `editor/editor.js:3584,3849` does not set `isEvalSupported: false`.

**Fix.** Upgrade SheetJS to 0.20.2 or later and pdf.js to 4.2.67 or later (or set `isEvalSupported: false`). Keep a `vendor/VERSIONS.md` with versions and hashes.

### S10 · Area codes are short for codes anyone can try

Low · Code · effort S · Next

Stockroom and Dock codes are 4 digits and the manager code 6, with no strength rule on the server, and the manager code alone signs in at the public sign-in. Guessing is capped at about 30 tries an hour per store, so a 4-digit code takes about two weeks of nonstop guessing (which also locks everyone else out, see S4). Store PINs older than the 6-digit rule are still accepted.

**Evidence**

- `worker/registry.js:256,296` hash codes with no length check; `js/views/admin.js:29-30` generates `SR-`/`BD-` + 4 and `MG-` + 6 digits.

**Fix.** Require longer codes when they are set (for example 8 or more letters and digits); consider asking for the PIN with the manager code; prompt rotation of short PINs.

### S11 · Smaller security items

Low · Code · effort S · Later

Grouped low-severity items.

- An anonymous request with a `null` body throws, and the error lands in the owner’s error list, so anyone can push real errors off it (`worker/index.js:24-27`).
- A malformed `%` in a path throws outside the request’s error handling, giving a bare 500 (`worker/index.js:284`).
- Device ids are chosen by the device, so a PIN holder can reuse a colleague’s id to see its draft photos, overwrite its heartbeat or lock its sign-in (`worker/index.js:27`, `worker/store.js:378,393,680`).
- No limit on sockets per device or per store (`worker/store.js:638-647`).
- Owner access tokens cannot be revoked within their 12 hours (open since the September audit).
- CI: actions pinned by tag, not commit; no `permissions:` block; the workflow prints the owner key’s length (`.github/workflows/deploy.yml`).
- A bare `wrangler deploy` would deploy the dev configuration over the production worker name (`wrangler.toml:9`).
- Product links from the legacy lookup are not checked to be `https://www.kmart.com.au` on the device (`js/views/stockroom/common.js`, `js/search.js:144,201`); the security policy blocks `javascript:` links anyway.
- Netlify publishes the whole repo, so `docs/` (including these audits), `test/` and `scripts/` are public (`netlify.toml` `publish = "."`). No secrets are in them.
- Worker responses lack `X-Content-Type-Options: nosniff`; the site has no HSTS header of its own.

**Fix.** Fix opportunistically; the CI and publish-folder items are a few lines each.

## 3. Performance and cost

What gets slow as a store’s data grows, and what Cloudflare bills.

### P1 · Product names fail on any screen that needs more than 50 of them

High · Reproduced · effort S · Fix first

The app sends every product code a screen needs in one request, and the catalogue refuses more than 50. The whole request fails, every product shows as “not online” with a search link, the failure is not remembered so it repeats, and then one “did you mean” request goes out per code. The Manifests products tab asks for up to 200, Stockroom intelligence up to 300 and Carton profiles 100. This is the likely reason product names on the live site went to Kmart’s search instead of the product page: my test manifest had only 8 products, so I missed it.

**Evidence**

- `client/catalogue.js:36` joins all queued codes into one request; `worker/catalogue.js:24,34` refuses more than `MAX_CODES = 50`.
- `js/views/stockroom/common.js:79` sends a near-miss request per unknown code.

**Fix.** Send in chunks of 50, remember failed codes for the session, batch near-miss lookups, and fetch page details in the background (`waitUntil`) instead of before answering.

### P2 · Attaching a manifest re-scans the whole consolidation ledger once per consolidation

High · Measured · effort S · Fix first

Each time a consolidation is recorded, the reducer prunes the entire 60-day ledger. A 300-consolidation manifest does that 300 times: 3.4 to 3.7 seconds per attach at a steady ledger, on the worker (which blocks the store meanwhile) and on every dock device, and about four times over on the device that attached it. Pallet scans pay the same cost on a smaller scale.

**Evidence**

- `shared/reducers/backdock.js:693` (inside `ledgerAdd`) filters every ledger entry on every call; called per consol (`:89`), per scan, and per staged id in `plan.set` (`:611`).

**Fix.** Prune once a day, in nightly retention. Expected: attach about 35 ms and scans under 0.2 ms.

### P3 · Every incoming change rebuilds a copy of the whole store on the device

Medium · Measured · effort M · Next

Each change received copies the whole state and turns every section into text to see what changed. On a manager device with a 3.65 MB state that is 100–140 ms per change on a desk PC and 600–700 ms on a mid-range phone; a burst of 20 changes froze a phone for 13 seconds in total. Floor-only phones hold much less and pay about 50 ms.

**Evidence**

- `client/store.js:69-72` (`structuredClone(base)` then `JSON.stringify` of every slice); `:123` clones again for every local change.

**Fix.** Skip the copy when nothing is queued; otherwise copy only the sections the queued changes touch, and work out what changed from the event itself. Expected under 5 ms. Shrinking the state (D3) helps too.

### P4 · The whole store is written to the device’s storage every two seconds

Medium · Measured · effort S · Next

While changes flow, the device saves the entire state every 2 seconds: 33–50 ms each time on a desk PC, 190–340 ms on a phone, on the main thread.

**Evidence**

- `client/store.js:97-101`.

**Fix.** Save per section, only when that section changed, at most every 30 seconds, plus once when the page is hidden.

### P5 · Location refresh freezes phones on a busy week

Medium · Measured · effort S · Next

The refresh screen repaints on every sync-status change (several per change), and matching marks to shelves compares every mark with every shelf. With 900 marks in the week, five incoming marks froze a mid-range phone for 22 seconds in total. Stocktake, Label integrity, Field Mode, Print map and Suggest edits use the same marking code.

**Evidence**

- `js/views/refresh.js:185` listens to `status`; `:93-96` canonicalises every mark per shelf; `js/map.js:514-517` searches the whole map per id.

**Fix.** Build a shelf index once per screen, index marks once per paint, and let the status listener update only the sync badge. Expected under 50 ms.

### P6 · The pick list’s route order is slow on a large map

Medium · Measured · effort S · Next

The new route-order check works out the best order and two walk lengths on every repaint, with a simple shortest-path search that slows sharply as the walk network grows. On a 750-point network with 20 stops one tick took 2.4 seconds on a desk PC and about 10 seconds on a phone. This came in with the route-order feature (PR #32).

**Evidence**

- `shared/route.js:50` scans every node to find the next one; `js/views/picklist.js:140` recomputes on every change; `routeLength` reruns searches the ordering already did; `js/map.js:101` searches all shelves per lookup.

**Fix.** Use a priority-queue search (10 to 400 times faster on these sizes), reuse the distance table for both lengths, remember legs, and run the check after the screen paints.

### P7 · Carton profiles read every manifest ever published

Medium · Measured · effort M · Next

Each request for carton profiles parses every stored manifest, and manifests are never deleted: 60 manifests took 1.5 seconds and returned 16 MB. Somewhere past 100–150 manifests this risks the store’s memory limit.

**Evidence**

- `worker/store.js:178`; manifests are deleted only by an explicit remove (`:454`).

**Fix.** Record arrivals per keycode when a manifest is published, prune manifests older than the 26-week window, and cache the result.

### P8 · Map screens hold old views in memory until a key is pressed

Low · Measured · effort S · Next

Each visit to a map screen on the desk leaves a keyboard listener behind that keeps the previous view alive: about 18 listeners and up to 2,200 page elements per visit in the measurement. The listener removes itself on the next key press, so a desk used only by mouse or touch piles them up over a shift.

**Evidence**

- `js/map.js:371` ties listeners to a per-stage controller that nothing aborts when the view changes; the `keydown` listener added to `document` at `:889` only removes itself on the next key press (`:882`).

**Fix.** Abort the previous mount’s controller when the view changes (`parkMap()` or `show()`), or pass the shell’s view signal into `mountMap`.

### P9 · Map zooming and dragging redo layout on every movement

Low · Measured · effort M · Later

Wheel zoom costs about 100 ms per step on a desk PC; dragging on a phone about 90 ms per frame. The first map open also forces two full layouts (2.5 seconds on a phone), which CLAUDE.md’s map rules say to avoid.

**Evidence**

- `js/map.js:503` reads layout on every wheel event; `:428` rewrites the viewBox and every marker; `:391` `getBBox` on mount.

**Fix.** Batch input per animation frame, use the size the resize observer already tracks, move a CSS transform during the gesture and commit at the end; store each floor’s fitted view when the map is published.

### P10 · Every device loads every screen at start-up

Low · Measured · effort M · Later

All 102 modules (709 KB compressed) load before sign-in, including the owner console and desk-only screens a phone can never open. Throttled to a mid-range phone on slow 4G, sign-in appeared after 5.8 seconds. A reload from the service worker is fast (0.4 seconds).

**Evidence**

- `js/registry.js:5-38` imports every view statically.

**Fix.** Load each screen on first use (`import()` from the registry). Estimated 40% less start-up code.

### P11 · Heartbeats keep each store awake all shift (the main Cloudflare cost)

Low · Estimated · effort M · Later

Twenty devices each sending a heartbeat every 3 minutes, plus one after each action, keep the store object awake for the whole shift. Estimated 162,000 GB-seconds per store per month: Cloudflare includes about 400,000 per account, so beyond two or three stores this is about US$2 per store per month. Requests, storage and rows are negligible by comparison.

**Evidence**

- `client/store.js:22,248-256`; `worker/store.js:668` replies to each heartbeat.

**Fix.** Use the WebSocket auto-response ping so heartbeats do not wake the object, and take presence and clock offset from that. Estimated 40–70% less duration.

### P12 · Smaller performance items

Low · Mixed · effort S · Later

Grouped low-severity items.

- The OCR, spreadsheet and barcode libraries (4.3 MB for OCR) are downloaded again after every app update, because they are cached in the release cache (`sw.js:36,86`). Give them a cache that survives releases.
- Backfill review renews its claim every 5 minutes as a logged event (about 120 per desk per day, kept forever), and bulk actions send one change at a time, each paying the full rebuild (`bfreview.js:95,324`, `intel.js:144`, `adjust.js:68`, `refresh.js:106`). Treat claims as presence; add a batch dispatch.
- History and export parse the whole archive for each page: 215 ms at two years of bays (`worker/store.js:187-191,344`). Page in SQL with an index.
- Sign-in password hashing (55 ms each, up to three per unlock) runs in the one registry object shared by all stores.
- Broadcast turns each change into text once per socket instead of once (`worker/store.js:714`).
- The owner console reloads a store’s whole state every 30 seconds on the Boards tab (`admin.js:184`).

**Fix.** Pick up alongside related work.

## 4. Operations and code

Deploys, environments, monitoring, tests and code health.

### T1 · The site goes live before the worker, so new features fail for a minute after each merge

High · Observed · effort M · Fix first

Netlify publishes the app as soon as a PR merges; the worker deploys about a minute later, after its tests. In that gap the new app sends changes the old worker does not know, and they are refused and deleted (D2). This is what happened with No trucks. In the other direction, a phone that has not tapped “Update now” silently ignores newer kinds of change, so its view drifts.

**Evidence**

- `.github/workflows/deploy.yml:35-51` (worker after tests; Netlify publishes independently).
- `client/store.js:88` ignores events its reducers do not know.

**Fix.** Deploy the worker first, check it is healthy, then publish the site from the same workflow (Netlify build hook or `netlify deploy --prod`, with auto-publish off). Have the worker report its build in `/v1/health` and the socket hello, keep unknown-type changes queued (D2), and prompt an old app to update when it meets a newer change.

### T2 · There is no separate production: every site and preview uses the pilot store’s worker

High · Code · effort M · Next

Every site origin, including Netlify’s PR previews, talks to the staging worker that Busselton uses, and every push to main updates it. A preview build can write real events into the live store. Production deploys run by hand from any branch with no approval, overlapping runs are not prevented, and the post-deploy health check never fails.

**Evidence**

- `js/config.js:5` (`WORKER_DEFAULT` is staging for every origin).
- `.github/workflows/deploy.yml:14-17,67-68` (manual target, `sleep 5; curl -s`).
- `wrangler.toml:9` (top-level name equals production’s).

**Fix.** Pick the worker by the site’s hostname (production site to production worker, previews to staging with a test store). Promote by tag through a GitHub Environment with approval, add a `concurrency` group, make the health check fail on a wrong build, and rename the top-level worker `conduit-dev`.

### T3 · Some owner console numbers are wrong

Medium · Observed · effort S · Next

Device presence lives only in memory, so after the store goes idle the console shows “0 devices seen”. “Backfill locations” and “dock records” count the sections of the data, not bays or trucks (an empty store shows 4 and 7). And Fleet cannot spot old app versions, because the app’s version string has stayed v0.3.0 since 9 October; the worker always says 0.1.0.

**Evidence**

- `worker/store.js:679-684` writes presence into memory only.
- `js/views/admin.js:229-230` counts object keys.
- `js/version.js` (`v0.3.0`), `worker/version.js` (`0.1.0`).

**Fix.** Keep presence in a small table (updated at most once a minute per device), count real bays and trucks, and stamp the build (commit) into both versions from CI.

### T4 · Nothing alerts anyone when something breaks

Medium · Code · effort S · Next

Worker errors go to a list on the owner Service page, which someone has to open. There are no Workers logs, no uptime check, no alert if the nightly run stops, and app errors on devices stay on the device.

**Evidence**

- `wrangler.toml` has no `[observability]` or cron; `worker/http.js` `reportError` keeps the newest 100.

**Fix.** Turn on Workers Logs; add an uptime check on `/v1/health` and the site; send an email or webhook for new errors, a missed nightly run, a store over 1.2 MB, or devices with stuck outboxes; include an app error count in heartbeats.

### T5 · No browser tests in CI

Medium · Code · effort M · Next

The 288 tests cover the worker and reducers well, but no test loads a screen. The four-size browser check in CLAUDE.md is manual, and CI runs in UTC although a Perth-only bug has shipped before. The Register a store crash (PR #34) would have been caught by a smoke test.

**Evidence**

**Fix.** Add a Playwright smoke test over every screen at the four sizes that fails on page errors or the “could not open” card, three end-to-end flows (refresh offline then online; backfill scan to submit; land a truck to finalise), and one test run with `TZ=Australia/Perth`. Add a `--seed` option to the dev stack so screens have data.

### T6 · Release notes and version numbers have stopped

Low · Code · effort S · Next

What’s New is still on v0.3.0 from 9 October, so it never shows, and the tour describes things phones no longer have (a store chip, a barcode button, theme colours).

**Evidence**

- `js/version.js`, `js/whatsnew.js:20`, `js/tour.js:11-17`.

**Fix.** Set the version in CI on each release, keep a one-line note per PR, and refresh the tour per device.

### T7 · Code health

Low · Code · effort M · Later

Grouped technical items that make change safer.

- Event versions: a change of `v` breaks older apps, the state version is never checked, and registry migrations rely on ignored errors (`shared/validate.js:21`, `shared/reducers.js:18`, `worker/registry.js:67`). Add upcasters and a schema version.

## Checked and sound

Tested directly and found to hold:

- **Sign-in tokens.** HMAC-SHA256 with constant-time comparison and expiry; the actor on every change comes from the token, never the device; cross-store access is refused on every store route; owner and act-as tokens are separated; act-as is capped at an hour.
- **Passwords and lockout.** PBKDF2-SHA256 at 100,000 iterations with salts (the Workers maximum); lockout counts per device, per store and per network; owner devices are exempt via a device secret.
- **Permissions on changes.** Every change is checked for role, area and tool switch on the worker; worker-only changes are refused from devices; prototype-pollution keys are refused anywhere in a change; all SQL is parameterised; photo keys are built by the server.
- **Site security policy.** Scripts only from the site itself, no inline or eval, `object-src none`, framing refused, `nosniff`; verified in the browser that injected scripts and inline handlers do not run. `?worker=` links can only point at the two Conduit workers.
- **Escaping.** Free text from other devices (messages, briefings, issue titles and notes, feedback, manifest numbers, product names, bay and cage ids, search results, print sheets) is escaped. The map SVG sanitiser held against every bypass tried.
- **Tokens on the device.** Never in URLs (the socket uses a subprotocol); stored in IndexedDB; sign-out revokes current, parked and act-as refresh tokens; the service worker never caches API responses.
- **Reducers.** 1,500 random changes per type across four seeds: no refusal changed state, nothing threw, no change object was mutated. 72,000 mixed dock and stockroom steps round-tripped through JSON with no divergence. No clock or randomness inside reducers.
- **Worker write path.** Duplicate ids are refused durably; a reducer that throws reloads the store from its log; SOH, report and manifest removal log their event first; nightly retention and photo sweeps are idempotent; the socket path keeps order.
- **Maps and caching.** Each published map is downloaded once and kept on the device; one live map element is reused across screens; the service worker serves a reload with zero network bytes; heavy libraries load only when used.
- **CI secrets.** Secrets reach the worker through stdin and are never printed; pull requests run tests without secrets; deploys run only on push or by hand.

## Method

- Five review passes ran in parallel, each instructed to tie every finding to code and to reproduce anything serious: worker and API security; app and map-editor security; data integrity and reliability; performance, efficiency and cost; product and technical suggestions.
